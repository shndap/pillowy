# Telegram Pill Tracker — Development Prompt

Build a polished, production-quality **Telegram Mini App for personal pill/medication tracking**.

The application is primarily for two people and should feel like a beautiful, thoughtful personal wellness app rather than a generic Telegram bot.

The application must be designed so it can be deployed **entirely on free tiers**.

# 2. CRITICAL ARCHITECTURAL REQUIREMENT: REMINDERS

Do NOT depend on a continuously running scheduler inside the FastAPI/Render process.

Render's free web service may sleep when idle.

Therefore:

```text
❌ BAD

Render
  └── FastAPI
       └── APScheduler
            └── waits for 08:00
```

Do NOT use this architecture for medication reminders.

Instead, the reminder system must be **scheduler-independent**.

The backend must expose an idempotent scheduler endpoint that can be triggered externally.

Conceptually:

```text
External Scheduler
       │
       │ periodic request
       ▼
FastAPI /internal/scheduler/tick
       │
       ▼
Find reminders that are due
       │
       ▼
Send Telegram notifications
       │
       ▼
Mark notifications as sent
```

The exact external scheduler can be selected during deployment, but the backend must NOT assume that the FastAPI process remains alive continuously.

The scheduler endpoint must be safe to call repeatedly.

If it is called twice for the same minute, the user must NOT receive duplicate reminders.

# 3. Scheduler Design

Create a scheduler service with a function conceptually equivalent to:

```python
process_due_notifications(now)
```

It should:

1. Determine the current time in each user's timezone.
2. Find all medication reminders that are due.
3. Determine which doses are still outstanding.
4. Create/send Telegram notifications.
5. Record that the notification was sent.
6. Never send the same notification twice.

Use a database-backed notification record or equivalent idempotency mechanism.

For example:

```text
notification_log

id
user_id
schedule_id
scheduled_for
notification_type
sent_at
```

Create a uniqueness constraint around the relevant notification identity.

For example:

```text
(user_id, schedule_id, scheduled_for, notification_type)
```

This prevents duplicate notifications if the scheduler runs multiple times.

---

# 4. Reminder polling frequency

The scheduler should ideally call the backend approximately once per minute.

The backend should NOT require exact-second timing.

For example, if a medication is scheduled for:

```text
08:00
```

and the scheduler runs at:

```text
08:00:12
```

the reminder should be sent.

If it runs at:

```text
08:01:03
```

it should still be able to recognize that the 08:00 reminder is due, assuming it has not already been sent.

Do not rely on:

```python
if current_time == scheduled_time:
```

because that is fragile.

Instead use a small due window / scheduled timestamp approach.

Each medication should contain:

# 9. CORE UX: PRESET "I TOOK MY PILLS"

The most common medication-taking action must require **one tap**.

The user should NOT have to repeatedly enter:

* medication name
* quantity

for normal scheduled medication.

For example, if the morning schedule contains:

```text
Vitamin D × 1
Magnesium × 2
```

the dashboard should show:

```text
[ ✓ I took my morning pills ]
```

When pressed:

1. Find all enabled morning schedules.
2. Determine today's doses.
3. Determine which doses have already been recorded.
4. Record only outstanding doses.
5. Decrease inventory accordingly.
6. Mark the scheduled doses complete.
7. Return a confirmation.

Example:

```text
✓ Morning pills recorded

Vitamin D ×1
Magnesium ×2

You're all set ❤️
```

The user should never be asked:

> Which pills?

or:

> How many?

for this normal preset flow.

# 10. Partial Completion

Users must also be able to record individual medications.

Example:

```text
🌅 Morning

✓ Vitamin D       1 / 1
○ Magnesium       0 / 2

[ Take Magnesium ]
[ ✓ Take all morning pills ]
```

If Vitamin D has already been taken and the user presses:

```text
✓ Take all morning pills
```

the system must NOT record Vitamin D again.

Only outstanding doses should be recorded.

Example:

```text
Initial:

Vitamin D   0/1
Magnesium   0/2

User takes Vitamin D:

Vitamin D   1/1
Magnesium   0/2

User presses "I took my morning pills":

Vitamin D   1/1
Magnesium   2/2
```

Inventory should decrease only for Magnesium during the second action.

---

# 11. Duplicate Protection

Medication intake must be idempotent.

Repeatedly pressing:

```text
✓ I took my morning pills
```

must never cause duplicate intake.

The backend must enforce this.

Do NOT rely only on frontend state.

The database/business logic should ensure that the same scheduled dose cannot be recorded twice for the same user/date.

Calculate remaining supply based on:

```text

```

For medications with multiple scheduled doses, daily quantity is the sum of all enabled scheduled doses.

Never allow inventory to become negative.

# 27. Atomic Medication Intake

Recording a dose must be transactional.

Conceptually:

```text
BEGIN

1. Find scheduled dose.
2. Check whether it has already been taken.
3. Check inventory.
4. Create intake record.
5. Decrease inventory.
6. Create inventory transaction.
7. Commit.
```

If anything fails:

```text
ROLLBACK
```

Never allow:

```text
intake recorded
but inventory unchanged
```

or:

```text
inventory decreased
but intake not recorded
```

# 28. Insufficient Inventory

Do not allow negative inventory.

The user may still be able to record a smaller manually entered quantity if the product design supports partial doses, but the normal preset action should not silently consume more pills than exist.

# 30. Scheduler Deployment

Because Render Free may sleep, do NOT rely on a continuously running background scheduler.

The backend should expose:

```text
POST /internal/scheduler/tick
```

An external free scheduler should periodically call this endpoint.

The scheduler endpoint should:

* be idempotent
* process missed reminders within a reasonable window
* prevent duplicate notifications
* use database-backed notification records
* handle timezone conversion
* handle multiple users
* handle multiple medications
* handle low-stock notifications
* return useful logs/status information

The backend should be able to safely process a scheduler tick even if it has been several minutes since the previous tick.

---

# 31. Scheduler Failure Recovery

If the backend was asleep or temporarily unavailable, the next scheduler invocation should be able to detect missed notifications.

Do not simply compare:

```text
current_time == reminder_time
```

Instead, store scheduled notification timestamps and process notifications that are:

```text
scheduled_for <= now
AND
not already sent
AND
within a reasonable expiration window
```

Do not send extremely old reminders after the user has been offline for hours/days.

The exact expiration policy can be configurable.

# 36. Important Product Principle

This application is a **tracker**, not a medical decision-making system.

The application should only track medications, schedules, quantities, inventory, and user-entered information.

Do not implement:

* medical recommendations
* dosage recommendations
* diagnosis
* drug interaction analysis
* AI medical advice
* automatic changes to prescribed quantities

The bot should remind the user about the schedule they configured; it should not decide what medication they should take.

